# WhiteRoom：3D PvE 白色測試場 Sample 實作計畫

> Task ID: white-room-stage0

依使用者指定，以既有 `com.yu5h1.combataesthetic` 套件的 Sample 發展。本文定義第一個可操作交付與實作順序；實際進度與驗證依 [Report](../../report.json) 及其證據判斷，本計畫不代替執行結果。

## 位置與關係

```text
CombatAesthetic Unity package
├─ Runtime／Editor：既有套件能力
└─ Samples~/WhiteRoom：白色空間 3D PvE 測試場
   ├─ 場景、機器人角色與測試情境
   ├─ 玩家／AI 的操作來源
   ├─ 移動／攻擊／防禦與受擊表現
   ├─ 第三人稱鏡頭、theme 與隊伍辨識
   └─ 重設與測試紀錄
       └─ 由相容 Unity 宿主匯入 → Editor 操作與 Windows 執行版驗證

data-driven repo（limb 與 animation 共用規劃；格式待釐清）
├─ 共用製作操作 → 已選最小 Web 入口，Web 共用套件在 Yu5h1Lib.Web 發展
├─ 固定人形骨架＋簡單幾何外殼 → WhiteRoom 首輪動作測試
├─ limb：結構、網格生成與修形 → 接入 WhiteRoom 驗證
└─ 跨平台資料 → Unity WhiteRoom 載入、呈現與戰鬥驗證；接用方式待釐清
```

Sample 的原始內容、資產與案例累積於此套件；Unity 宿主負責載入套件、匯入 Sample 與建置。宿主是執行驗證環境，不取代 Sample 的交付歸屬。本計畫取代先前另建獨立產品專案承載白色空間的提案。

共用形體與動作系統已整合至 `Yu5h1Lib/data-driven`，整體分工由 [Data-driven 計畫](../../../../data-driven/plan.md) 擁有，動畫細節見 [Animation 計畫](../../../../data-driven/animation/plan.md)。Combat Aesthetics 專注戰鬥整合，WhiteRoom 保留資料接用與戰鬥驗證；此次整合未實作來源系統。

本輪驗證宿主使用現有 `W:/UnityProject/Yu5h1LibTest`，Unity `6000.6.0f1`、URP；取代原先 `6000.3.9f1` 的首輪宿主選擇，不降版或另建專案。依賴、設定與場景內容須可追溯，沿用 Combat Aesthetics 及所需 Yu5h1Lib 套件；套件與跨平台資料接用相容性仍須實測，選定版本不等於驗收通過。

## 問題與目標

WhiteRoom 需要以可累積、可重用的方式驗證第三人稱徒手 PvE，以及跨平台資料驅動的 runtime 動作製作。階段 0 先取得既有能力、宿主依賴及可觀察案例的具體證據，使後續實作建立在 Yu5h1Lib 的累積與已確認 UX 上。

目前可交給其他 agent 的是下文限定的準備工作；兩種測試共用操作流程與首輪 Web 製作入口已確認，具體編輯細節、資料格式及接用設計依 Animation 計畫逐題釐清。

## 第一個交付的目標

唯一實際測試者為使用者本人。讓使用者在白色測試場控制 3D 角色與 AI 交戰，反覆測試基本操作、動作與接觸後果，快速重設後比較結果。

| 已確認範圍 | 第一個交付必須可觀察的結果 |
|---|---|
| PvE | 玩家能與 AI 角色交戰；同一角色條件下，玩家與 AI 遵守相同出招、防禦、受擊及恢復限制。 |
| 移動與跳躍 | WASD 以鏡頭畫面為基準作八方向移動，角色轉向輸入方向前進；Space 可跳躍，能看出起跳與落地。 |
| 原地攻擊 | 未輸入移動方向時能出招，有可見動作、命中時機與基本接續／恢復區間。 |
| 方向攻擊 | 方向輸入能指定出手方向，包含向畫面近處或側方的目標出招。 |
| 普通防禦 | 右鍵進入警戒，角色自動嘗試防禦面向範圍內的攻擊；仍受能力、姿態與動作限制，背後不自動擋。 |
| 精準防禦 | 玩家能抓時機操作精準防禦，並觀察與普通格擋不同的反應；首輪操作與效果提案見下文，數值不在計畫中硬定。 |
| 受擊與恢復 | 命中、成功防禦與失去控制有可辨識的反應；角色按目前狀態的動作區間恢復，動作切換不能任意取消原有受力。 |
| 第三人稱鏡頭 | 玩家能看見自己的角色與周圍威脅，角色接近畫面中央；鏡頭轉動不強制改變角色朝向。 |
| 快速重設 | 能回到相同情境的起始配置，重試不同操作，不累積上一次受擊、速度、AI 目標或命中紀錄。 |
| runtime 動作製作 | 依 Animation 計畫的 Web 製作流程調整姿勢與動作時序、即時預覽、保存跨平台資料，重新載入後能重現；WhiteRoom 能接用資料驗證動作。首輪以簡單固定骨架方式驗證，具體接用方式仍待評估。 |

第一個交付以「可操作完整 PvE 循環」為完成程度，不能只交一個角色走動的場景。細部招式、姿態連段、受身、全部物種、全部社交互動與完整電影動作仍逐步發展；已確認的 PvP／協作需求保留在後續路線，不因首交聚焦 PvE 而刪除。

首輪已確認採徒手，驗證移動、攻擊、防禦與受擊的完整循環；模型與動畫選材以此為範圍。武器在後續加入，首輪不以武器模型、握持與裝備接合為前置條件。

## 美術與角色方向

已選方向為素面白色的簡化機械人形與白色測試場。首版以最簡單可用的方式呈現，簡單或卡通風格也可接受；接近真人比例是原先參考，不作為素材採用的硬性門檻。角色保留可辨識的朝向與關節，透過實際骨架動作呈現移動、攻擊、防禦與受擊，先確保動作可讀。

首版使用上述素面白色的基礎素材，先支援操作、朝向、接觸與動作判讀。舊版模型、材質與動畫素材暫不納入本輪選材，也不以整理或重定向舊素材作為前置工作；既有程式與機制仍依能力對照評估重用。

白色基礎角色已確認也由 agent 製作，首輪採固定人形骨架搭配簡單幾何外殼，模型與骨架來源一起保存，供重建、修改與後續動作適配。製作資料採跨平台方向，Unity 端如何接用仍需驗證。肢體系統之後也在 WhiteRoom 測試，兩種方式共用操作流程已確認，資料接用邊界尚待釐清。

動畫已確認改由 agent 建立並累積自己的動畫庫，先補齊徒手首交的移動、跳躍、攻擊、防禦與受擊／恢復，再逐步調整表現。具體模型檔、骨架、動畫製作與保存方式及適配仍需確認；方向已定，不表示動畫或製作工具已完成。

模型與動畫已確認必須能合法隨 Sample 一起提供，完成宿主必要套件安裝並匯入 Sample 後即可測試，不要求使用者另外註冊素材服務或下載資產。選材時逐項核對再散佈及修改條件，保存作者、來源、版本與授權文件；僅允許放入遊戲執行版的素材，不足以滿足可提供原始資產的 Sample 需求。

細部製作提案：

- 外殼採霧面淺色，關節較深，頭部與正面方向清楚，便於判讀重心與接觸位置。
- 場地用簡單幾何、淡格線、接觸陰影與克制光照，使角色與地面可區分。
- 外殼、關節與隊伍標示分開配色；亮／暗版本依系統 theme 切換，隊伍顏色保持各自用途。
- 角色與場景設定可重用；具體色碼、材質及陰影仍需操作畫面確認，不因風格已定就視為模型或動作品質已驗證。

首輪從人形建立循環，之後增加非人形素體驗證延伸性。肢體描述、自動 mesh 與生長由 data-driven 的 limb 模組規劃，WhiteRoom 保留消費端案例；完整肢體生長功能不是首交門檻。

### WhiteRoom 的兩種動作測試

| 方式 | 角色與動作來源 | 驗證順序與邊界 |
|---|---|---|
| 簡單方式 | agent 製作的固定人形骨架、簡單幾何外殼及跨平台動作資料。 | 首輪先驗證 runtime 調姿勢／時序、預覽、保存及重載，再接到徒手 PvE 操作與反應。 |
| 肢體系統 | 獨立肢體系統提供的描述、形體與動作能力。 | 之後接入同一 WhiteRoom 作另一種動作測試；具體案例與接用方式另行釐清，不預設動物、樹枝或生長功能都要首輪完成。 |

兩種方式已確認共用同一套姿態／時序調整、預覽、保存與重載操作流程，並共用 WhiteRoom 作測試環境。角色結構的接用方式各自評估；共用操作不自動等同使用完全相同的資料語法、骨架表示或實作介面。

### 製作介面與驗證宿主

共用動畫系統的方向與製作流程由獨立 [Animation 計畫](../../../../data-driven/animation/plan.md) 擁有；Web 共用套件與正式動畫格式規範依該計畫的歸屬接用，不在此複製規範。WhiteRoom 的載入、動作與戰鬥驗證使用上述 Yu5h1LibTest／Unity `6000.6.0f1`／URP 基準。

WhiteRoom 需要能接用該系統保存的資料，對照預覽、重新載入後的動作與實際戰鬥反應。具體接用與是否即時連線尚未定案；本套件不自行建立動畫製作介面或替系統選定資料格式。

### 自有動畫庫

共用動畫系統的目標、跨平台資料、製作／播放與來源保存由 [Animation 計畫](../../../../data-driven/animation/plan.md) 擁有，本節保留 WhiteRoom 的消費端要求。

WhiteRoom 使用自有動作驗證角色依狀態播放、混合，再疊加受力與姿態修正的結果。必須保留重量、來勢與原有受力因果，不能因切換動作就清除擊飛或瞬間恢復站姿；精確動作、骨架適配、接觸與恢復的可讀性仍須後續驗證。

[既有能力對照](Existing-Capabilities.md) 是此消費端的重用證據，包含 Editor／Clip 耦合的限制；不能因共用系統尚未實作，就將 Clip 寫入工具改回必要管線，或自行重寫已存在的通用機制。本輪只規劃與整理接用要求，不實作動畫系統或格式。

## 套件與 Sample 邊界

### 模組化累積與重用

新舊戰鬥基礎先在同一 repo 建立隔離邊界，由 WhiteRoom 驗證；遵循 [已確認的演進與遷移方向](../../Documentation/plans/UPM-Package-Split-Plan.md#已確認的演進與遷移方向)。WhiteRoom 不直接接管舊 GameManager，也不能以永久另寫一套 Sample 戰鬥框架取代可重用能力。KFC 遷移由使用者在另一個 session 處理，不屬於本工作範圍或 WhiteRoom 完成條件。

使用者的目標是讓每輪開發累積可重用的技術。開始實作前，先盤點既有 Yu5h1Lib 與 CombatAesthetic 的能力與慣例，確認相容性及缺口，再決定重用、擴充或新增；AI 不能只依一般遊戲範例另寫一套相同機制。

| 層次 | 在此計畫中的責任 |
|---|---|
| Unity 驗證宿主 | 提供選定的 Editor、URP、套件引用及執行／建置設定，匯入 Sample 作驗證；不成為共用技術的另一份實作來源。 |
| Yu5h1Lib 共用套件 | 優先重用已存在且相容的機制；多個用途需要同一行為時，依既有歸屬擴充，不複製到 Sample。具體採用清單先查來源與測試，不只憑套件名稱判定可用。 |
| data-driven／animation 模組 | 共用動畫資料與播放的目標見其計畫；與同 repo 的 limb 接用，本套件保留消費端要求與驗證。 |
| CombatAesthetic | 擁有對戰相關的共用規則與整合；Sample 需要的可重用戰鬥能力回到其適當位置累積，避免每個場景各有一套判定。 |
| WhiteRoom Sample | 組合角色、鏡頭、情境、主題與測試入口，保存示例資產與配置，示範既有能力如何共同工作。 |

此套件目前的 manifest 已宣告 `com.yu5h1.library`、`com.yu5h1.common` 與 `com.yu5h1.2d` 等依賴。宿主需安裝這些實際必要依賴；這不表示將所有 Yu5h1Lib 套件或舊 2D 實作不加檢查地套用到 3D。

階段 0 以 [既有能力與重用依據](Existing-Capabilities.md) 為具體起點，已對應輸入、3D 移動契約、接地／髖部修正、鏡頭、動畫協調、既有戰鬥限制、AI 路徑及 theme。後續為每個首交需求補齊「來源／版本、接用方式、驗證證據、缺口、預計擴充位置」。有缺口時先確認最窄的擁有者，再提出擴充；涉及其他專案的改動按需求流程處理，不在盤點中順手修改。依賴與行為重用都要有證據，不能把「使用 Yu5h1Lib」當成只加入引用而實際仍重寫機制。

### 來源與匯入

本計畫位於 `Samples~/WhiteRoom`，與 Sample 來源一同累積；本輪文件調整不更改 `package.json`、場景或程式。

依查核的 [Unity 6.3 Sample 文件](https://docs.unity.com/en-us/engine/6000.3/manual/packages-list/cus-pkg-lp/cus-pkg-development/cus-samples)，開發原始內容可放在 `Samples`，封裝時轉為 `Samples~`，供使用者匯入宿主的 `Assets`。後續需按實際釘選的 Editor／分發方式核對登錄方式，再選 `package.json` 或 `.sample.json` 作唯一登錄來源，避免混用。

建議未來結構如下，目前僅有本計畫及既有能力對照文件：

```text
Samples~/WhiteRoom/
├─ Implementation-Plan.md     本計畫
├─ Existing-Capabilities.md   既有程式與重用依據（已建立）
├─ README.md                  匯入、控制、重設與驗證入口
├─ Scenes/                    WhiteRoom 場景
├─ Prefabs/                   機器人、AI 與場景機制
├─ Art/                       模型、材質、動畫及來源／授權紀錄
├─ Runtime/                   Sample 的場景組合與執行邏輯
├─ Editor/                    確有需要才加入的 authoring 工具
├─ Settings/                  情境、角色能力與主題設定
└─ Tests/                     針對規則、重設及接觸結果的檢查
```

Sample 輔助程式不得靠宿主的 Assembly-CSharp 或特定機器絕對路徑才能運行。後續分別設定 Sample Runtime／Editor／Tests 的 assembly 邊界，讓宿主匯入後的依賴明確；不把 Sample 的場景組合反向放進既有 Runtime。

### 既有 2D 套件的處理

目前套件 [package.json](../../package.json) 仍有 2D 與其他 Yu5h1Lib 依賴；[Runtime assembly](../../Runtime/Yu5h1Lib.CombatAesthetic.asmdef) 也引用既有能力。Sample 即使另設 assembly，也不能避開套件本身的編譯問題。

所以先在選定宿主驗證「安裝此套件、尚未匯入 Sample」能否解析與編譯，再處理 3D Sample。若遇既有依賴問題，記錄具體缺口並提出最小相容處理，不能為此自動展開整包升級、2D→3D 改造或舊拆包計畫。

可以借用舊行為與資料概念；3D 碰撞、骨架與移動不能直接假定舊 2D 類別適用。只有已辨識、確實需要共用的能力才規劃回套件 Runtime，避免為首版建立整套新通用框架。

## 最小行為設計提案

這裡描述責任與資料流，實作型別及公開 API 尚未定案。

| 責任 | 第一輪要做的事 |
|---|---|
| 玩家／AI 操作來源 | 產生移動方向、攻擊、防禦等意圖；共用角色合法性判斷，不直接播放繞過限制的結果。 |
| 角色執行 | 依姿態、動作區間與能力接受或拒絕意圖，切換目前主要動作／反應。主動類別為移動（含閃避）、攻擊、防禦；反應先涵蓋受擊及防禦成功。 |
| 攻擊與接觸 | 依動畫的有效區間開關攻擊接觸；分辨自己、目標、攻擊實例與已處理命中，避免同一次接觸重複計傷。方向與身體位置要能對照動作。 |
| 防禦結果 | 依警戒、面向、當前區間與能力判斷普通防禦；精準防禦由玩家時機操作觸發，不要求角色自動反應先成功。 |
| 動作與受力表現 | 將已成立的結果呈現為動畫、位移與聲音，保留重量與受力因果；不把播放反應動畫當作判定本身。 |
| 情境與重設 | 保存角色、隊伍、起始位置、能力及 AI 配置；重設時按實際狀態清單清除殘留，再恢復基準。 |
| 鏡頭與主題 | 提供角色／威脅可讀性，與戰鬥狀態分開；切主題不改碰撞、能力或判定。 |

精準防禦首輪建議先驗證已確認的無方向操作：在來襲時機快速按下放開右鍵，成功時中止對方原本連續進攻。順向卸力、逆向彈開與更多方向技巧保留延伸；首交須實際具有精準防禦，不以所有方向變體尚未齊備為理由整項延期。確切時間窗與具體動畫來源於實作前收斂。

## 分階段實作順序

預計為大型實作、跨系統整合；目前文件修改範圍僅本計畫、既有能力對照、其 Unity metadata 及續接入口。每個階段是未來工作，不表示已執行。

### 可先交辦的準備工作

### 第一階段工作分解

第一階段目標是可持續擴充的連線攻防測試環境：使用者能開啟兩個獨立執行個體，各自控制角色，測互相攻防與共同面對 AI；從紀錄比較操作、正式結果與畫面，重設後可重試。首輪維持白色場景、簡化人形、第三人稱鍵鼠操作，不等待完整角色與動畫製作系統。KFC 遷移不在本階段範圍。

以下批次細化既有階段 1，不是新的平行 roadmap。每批以真實案例收尾；可沿用已有實作，但必須提供對應證據。

| 批次 | 工作與交付 | 進入下一批的條件 |
|---|---|---|
| A：來源與隔離邊界 | 核對套件及宿主匯入副本版本，建立本輪實作基準；將首輪所需能力逐項對應為既有重用、既有擴充或新增。列出可重用戰鬥邏輯的擁有位置、Sample 組合責任、2D／舊管理器相依與自動初始化影響。 | 每項新能力有明確來源與歸屬；新基礎的依賴方向不回到舊 GameManager／2D 角色，且不以改壞舊使用端換取隔離。實際 assembly／package 邊界以盤點結果決定。 |
| B：單一規則的最小循環 | 本機玩家與 AI 經相同規則完成移動、跳躍、一招原地／方向攻擊、普通／無方向精準防禦、受擊恢復與失去戰力；接上全場重設。 | 能辨識出招與命中時間，成功精準防禦確實中止對方進攻；同次出招不重複計傷，重設無殘留。先完成自動行為檢查與基本操作證據，再擴充表演。 |
| C：連線決策與最小接線 | 依已確認的玩家開房兼任主機模式，評估相容網路方案；定義操作來源、角色所有權、共同時間、出招識別、正式狀態及呈現邊界。 | 網路方案有選擇理由與最小驗證案例；未確認的操作回饋、輸入生效時間或補償政策不能由 agent 偷換成預設規則。選定與取得依賴遵守工作區授權流程。 |
| D：兩個獨立執行個體 | 接入真實傳輸，完成開房／加入、角色配置、共享戰鬥與重設。同機兩程序先驗證，再到兩台電腦 LAN；兩端各有自己的遊戲狀態與畫面。 | 最小 PvP 與共同面對 AI 的案例皆有跨端紀錄；一個程序內的 2P 操作或輸入延遲佇列不算雙端連線通過。 |
| E：網路條件與結果修正 | 加入已記錄的延遲、抖動、丟包條件，輪換主機／遠端位置；驗證精準防禦、同時出手、攻擊中止、重複／過時訊息與全場重設。 | 使用下節連線基線案例，能說明輸入何時生效、正式結果如何產生、兩端如何修正；容許差異需先明定並交由使用者確認手感。 |
| F：可重現交付 | 固定套件 commit、宿主／Editor／依賴版本、情境設定及測試條件；提供 Editor 與 Windows 入口、操作說明、紀錄和未達項。 | 另一個執行環境可按記錄重現；未實跑雙機、建置或視覺案例不得標為通過。第一階段完成不等於完整 PvE 首交、線上服務或全部 UX 完成。 |

連線資料契約最少要能辨識：是哪個場次與角色、哪次輸入／出招、所依據的時間，以及正式結果。持續狀態（移動、按住防禦）與一次性操作（出招、跳躍、按下／放開）須分清；遺失或重複訊息不能造成永久按住、重複攻擊或重設後重新受擊。具體序列化與傳輸方式由批次 C 評估，不先綁定套件 API。

下一個可交辦單位是批次 A 的來源與隔離設計，接著依已確認邊界補驗批次 B。批次 C 的權威模式、本機立即回應、有上限的延遲補償及主機中斷處理方向已確認；可據此盤點方案，補償與同步細節仍見「尚未決定」，不提前定案或建立空的網路框架。

### 連線驗證路線

以線上版需要的同步原則設計，先在本機與區域網路落地驗證，再擴到網際網路，最後發展雲端規模、玩家註冊及紀錄服務。LAN 是同一套多人戰鬥的初期測試環境；戰鬥規則、操作指令、角色／出招識別及狀態訊息應可沿用。網際網路的連線建立可能改用中繼、穿透或專用伺服器，與戰鬥判定保持清楚界線。此輪更新計畫，不啟動服務、安裝網路套件或實作同步。

| 階段 | 驗證重點 |
|---|---|
| 本機雙執行個體 | 同機啟動兩個獨立遊戲執行個體，驗證加入、各自控制角色、共享情境及重設。用最小移動／跳躍、攻擊、防禦與受擊恢復循環，記錄輸入、正式判定與兩端呈現，不能只播放相同動畫就算連線成立。 |
| 區域網路兩台電腦 | 各自執行 WhiteRoom、各控制一個角色，測互相攻防及共同面對 AI；玩家與 AI 走相同合法性規則。輪換主機與遠端角色，比較兩端所見、正式結果及全場重設。 |
| 第一階段網路條件測試 | 在同機／LAN 環境加入延遲、抖動與封包遺失，測精準防禦邊界、雙方同時出手、攻擊中止與結果修正。保留無額外延遲的基準；LAN 順暢不代表線上驗收通過。 |
| 網際網路小規模 | 在相同遊戲規則下驗證跨網路連線、斷線及延遲；評估直接連線、穿透或中繼的適用性與部署方式，不將輸入 IP 視為一定能跨 NAT／防火牆。 |
| 上線與規模化 | 再評估專用伺服器、雲端部署、身分、玩家紀錄、配對及運維；供應商與服務不在本輪選定。 |

視訊／遠端操作傳送畫面與輸入，和多個客戶端各自呈現並同步同一場戰鬥是不同的驗證目標。前者可以協助遠端測試，但不能替代後者的攻防一致性證據；若之後需要遊戲串流，再另定案例。

基礎設計先辨明控制來源、角色／出招識別、共同時間依據、命中與防禦結果由誰裁定，以及狀態修正、全場重設與資料版本的界線。本機玩家、遠端玩家與 AI 提交操作意圖，經過相同角色合法性規則；畫面表演接收判定結果。先盤點 Yu5h1Lib 既有能力，再確定重用／擴充位置，不以 Sample 另寫所有通用機制。

首輪採玩家開房兼任主機（Host／Listen Server），其他玩家連入。主機裁定正式命中、防禦、傷害、受擊與恢復結果，AI 同樣由主機經共同規則處理；主機自己的玩家操作也遵守同一套合法性規則。戰鬥判定與本機畫面呈現分開，保留日後將判定端移至專用伺服器的空間，本輪不要求交付專用伺服器。此決策不代表主機與遠端延遲相同，仍需輪換角色測試。

本機移動與出招先立即回應，再依主機正式結果修正位置、動作或狀態。客戶端先呈現的動作不代表正式命中、格擋成功或傷害已成立；這些結果仍由主機裁定。主機拒絕出招或回報不同狀態時，本機必須能接回正式結果。具體預測、修正方法與可接受的呈現差異仍需驗證，此決策不等於已選定完整回滾方案。

首輪以最多 2 名玩家與 2 名 AI 作為驗收規模，人數依測試情境可配置，涵蓋玩家互打、共同對敵與多方威脅。此規模只界定首輪驗收，不作為正式遊戲上限；較大規模的效能與同步表現另行實測。

首輪 AI 採可設定、可重複的簡單攻防行為，能接近目標、出招與防禦，暫不要求複雜戰術。重複的是行為設定，不是強制相同戰鬥結果；受擊、攻擊中斷與恢復限制正常生效，不能為了維持固定節奏而繞過共同角色規則。

第一階段由開房者統一切換測試情境與執行全場重設，其他端同步採用同一份情境設定與重設結果。情境切換須同步還原該情境的起始狀態，避免兩端繼續執行不同情境；這是開發測試的控制方式，正式遊戲的模式管理另定。

第一階段開房後顯示主機的區域網路 IP 與連接埠，另一端輸入後直接加入。同機雙執行個體使用本機位址連線；跨電腦驗證使用可達的 LAN 位址。自動搜尋房間與邀請碼留待後續，直接輸入位址不代表已驗證網際網路連線。

第一階段主機離開或被判定斷線時，結束本次測試，向仍在執行的客戶端顯示可確認的原因，再由使用者重新開房。無法判明實際原因時顯示連線中斷，不將逾時推定為主機主動離開。主機轉移留待後續；新房間須與上一場分開，舊連線的延遲訊息不得影響新測試。

採用有上限的延遲補償。遠端操作較晚抵達時，主機可在有限範圍內查核過去的操作與戰鬥狀態，再裁定格擋等結果；具體補償上限留待 Demo 實測，不預先指定毫秒數。查核需對齊共同時間與動作合法性，不把客戶端宣稱的時間直接當成事實，也不保證畫面上看似成功即一定成立。時間驗證、超限處理及攻守公平性仍須在實驗中明確記錄。

同步協定與網路套件尚未選定。預測、遠端插值、結果修正與延遲補償皆須納入第一階段設計與實驗，但不要求第一輪實作完整回滾系統。實驗須區分操作採集時間、主機收到時間、歷史查核時間與正式裁定結果，以及向雙方呈現修正的方式。

本地預測處理操作的立即回應；遠端插值銜接其他角色的呈現；結果修正處理預測與正式結果的差異；回溯判定／延遲補償決定過去操作是否有效。這些能力的需求取決於遊戲互動與網路條件，LAN 與線上可使用同一方案；不能因 LAN 延遲低就省略相關驗證，也不承諾換網路後無需調整。

首輪提供可開關的除錯面板，顯示網路延遲、角色狀態、主機判定與修正事件，並可匯出該輪測試紀錄。面板區分本機預測與主機正式結果；延遲標示量測方式與單位，模擬條件另列，尚無連線量測時標為不可用。紀錄沿用場次、角色、輸入／出招識別與共同時間，附版本及情境設定，讓兩端能對照同一次攻防。關閉面板不改變戰鬥規則，正式體驗仍以身體與聲音提供資訊。

線上戰鬥沒有玩家個人的暫停。操作面板、切換視窗或離開電腦，都不會凍結世界或角色，也不提供無敵、免受擊或其他保護；角色仍可能被攻擊、失去戰力或死亡。玩家需要自行撤到安全位置再處理其他事情，系統不保證離席安全。主機切換視窗時也須維持整場模擬；主機失去連線則依既定中斷規則結束測試。

操作除錯面板、由面板取得輸入焦點時，停止該玩家的戰鬥輸入與滑鼠鏡頭控制，保留面板操作；僅顯示觀察資訊不等於取得操作焦點。整場戰鬥繼續，AI、其他玩家及既有受力、動作與恢復計時仍按規則推進，不因面板操作暫停或取消已成立的動作。面板操作期間的攻擊、跳躍與防禦輸入不排隊、不補發；返回戰鬥後須重新按下才生效。若返回時該鍵仍按住，須先放開再按下，不將面板期間的按住或放開判為戰鬥操作或精準防禦。

第一階段的連線基線案例：

| 案例 | 可觀察的完成條件 |
|---|---|
| 開房與直接加入 | 主機顯示連線位址與連接埠；另一端輸入後可加入同一場測試。同機與 LAN 分別留證，失敗時顯示連線未成功。 |
| 控制與共享移動 | 每端只控制被授權角色，移動與跳躍可在另一端觀察；記錄正式狀態及呈現偏差。 |
| 攻防一致性 | 同一出招不重複計傷；普通格擋、精準防禦、受擊及攻擊中止的正式結果在兩端一致。 |
| 玩家／AI 共用規則 | 玩家互打與共同面對 AI 均經相同出招、命中、防禦及恢復限制；重設後可重用相同 AI 行為設定，驗證接近、出招、防禦及遭中斷後的恢復，不以固定腳本強制出招成功。 |
| 情境切換與全場重設 | 開房者切換情境或重設後，兩端採用同一設定；玩家、AI、速度、生命、計時與出招紀錄回到該情境基準。其他端不能自行改變全場設定；舊情境的延遲訊息不污染新情境。 |
| 主機中斷與重新開房 | 分別測主機主動離開及失去連線，剩餘客戶端結束該場測試並顯示原因；可重新開房加入，新場次不接收舊場次的戰鬥結果。 |
| 除錯觀察與匯出 | 可切換面板並匯出本輪紀錄；操作面板時不觸發該玩家的戰鬥輸入或滑鼠鏡頭轉動，戰鬥仍持續且該玩家仍可受擊；切換視窗也不暫停世界。回到戰鬥不補發面板期間的攻擊、跳躍或防禦，重新按下才生效。兩端可依場次與出招識別對照輸入、主機判定及修正，實際延遲與模擬設定可區分。 |
| 不良網路與修正 | 記錄測試條件、輸入時間、判定時間、兩端呈現與修正；能重現精準防禦邊界及同時出手的差異。 |

執行前需記錄延遲／抖動／丟包設定、時間單位與延遲是單程或 RTT，並選定可接受的操作回饋、狀態偏差與修正幅度。數值尚待實驗定案；案例可執行或訊息可傳送不等於已達手感驗收。每輪保留版本、條件及結果，供擴充 gameplay 後回歸。

參考依據：[Unity 連線配置](https://docs.unity.com/en-us/mps-sdk/session-networking) 區分直接連線與中繼等方式；[Unity 延遲說明](https://docs.unity3d.com/Packages/com.unity.netcode.gameobjects@2.4/manual/learn/dealing-with-latency.html) 說明時間差、權威、預測與修正；[Network Simulator](https://docs.unity3d.com/Packages/com.unity.multiplayer.tools@2.2/manual/network-simulator.html) 提供不良網路條件測試的參考。引用不代表選定套件。

## 首交驗收案例

| 案例 | 預期觀察 | 證據方式 |
|---|---|---|
| Sample 匯入與建置 | 在記錄版本的宿主安裝套件、匯入 Sample、開啟場景並啟動 Windows 版本。 | 套件／Editor 版本、匯入路徑、編譯與建置結果。 |
| runtime 製作與重載 | 在選定製作介面以簡單固定骨架調整姿勢與時序，立即預覽並保存；重新載入資料後能重現，WhiteRoom 能接用相應動作。 | 製作介面修改前後畫面、跨平台資料及重載／WhiteRoom 接用後動作對照。 |
| 移動與鏡頭 | 八方向移動含畫面近側方向，角色轉向前進；能跳躍與落地，鏡頭跟隨且看得到自己與周圍。 | 使用者操作畫面、輸入與方向紀錄。 |
| 原地／方向攻擊 | 未輸入方向可出招，有方向時朝指定方向出招；空揮與命中有可辨識差別，同次攻擊不重複計傷。 | 動作時間、接觸事件與實際畫面。 |
| 普通防禦 | 警戒下嘗試擋面向範圍內來襲，成功有反應；被動反應速度隨角色能力變化，背後不自動擋。 | 能力配置、面向、攻擊事件及防禦結果。 |
| 精準防禦 | 玩家在允許的姿態／區間抓準時機，成功後中止既有連續進攻；不因角色自動反應慢就一律失敗。 | 輸入時機、動作區間及攻擊中止事件。 |
| 受擊與恢復 | 反應方向與來勢可理解，維持受力及合理位移，按當下主要狀態恢復。 | 狀態事件、速度／受力資料與動作畫面對照。 |
| PvE 與多方配置 | AI 可實際交戰；同樣條件下不跳過規則，情境能配置多個 AI 同時參與。 | 角色／AI 配置、動作許可與交戰畫面。 |
| 重設與主題 | 交戰或受擊後重設，還原情境基準；亮／暗 theme 與隊伍可分辨，主題不改判定。 | 重設前後狀態、兩主題畫面與結果對照。 |

自動檢查用於動作許可、有效區間、重複命中與重設殘留；使用者確認操作手感、鏡頭、輪廓及動作連貫性。正式體驗以身體與聲音提供資訊，避免常駐血條／耐力條；開發觀察工具另行開關，不把它當作正式戰鬥 UI。

## 後續發展邊界

- PvP／多人協作擴充：沿第一階段已驗證的共同戰鬥流程，增加多方情境、合作誤傷與網際網路測試；基礎多端攻防與延遲驗證已納入第一階段。
- 移動、受力及形態：保留短移步閃避、更多姿態、受身與第二種形態的需求；非人形使用自己的骨架與動作。
- 隊友互動：碰拳仍是第一個互動案例，由 AI 邀請、使用者回應；可產生碰拳、落空尷尬、遠距招呼等反應。尷尬依情境自動觸發，先不展開表演細節。
- 肢體生成系統：之後在 WhiteRoom 加入第二種動作測試；markup、mesh 生成與生長仍保留獨立歸屬，與簡單方式共用操作流程，資料與接用方式待釐清。
- 跨平台累積：保存 UX、案例、設定、原始資產與實驗結果；引擎動畫、物理、材質與網路整合仍需各平台適配與重驗，不承諾零重工。
